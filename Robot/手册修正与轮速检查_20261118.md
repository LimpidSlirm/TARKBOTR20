# 手册修正与轮速检查

日期：2026-11-18。修改对象是桌面新解压的 `TARKBOTR20-binimiya-patch-1/TARKBOTR20-binimiya-patch-1`，工程入口为 `Project/xproject.uvprojx`。此记录区分源码配置、离线检查和实车结论。

## 手册依据和采用的配置

依据《竞赛小车底盘培训手册 安装清单与STM32篇》的硬件清单、1.3、安装步骤 8、8.2、8.3、9.1、9.2，以及《塔克创新 R20系列机器人底盘开发手册 V1.2》第 15—17 页。原始手册没有修改。

| 项目 | 新文件夹原先实际编译的代码 | 本次修正 |
| --- | --- | --- |
| 车型 | 麦轮 `ROBOT_MEC` | 四轮差速 `ROBOT_FWD` |
| 电机和轮径 | FWD 示例是 P60、100mm | P30、65mm，即 0.065m |
| 每轮编码器计数 | FWD 为 3120；麦轮为 1560 | 磁编码器 1024×30×4=122880 |
| 轮距和系数 | 0.200m、1.75 | 保留为手册起点，尚未实测标定 |
| FWD 反馈符号 A/B/C/D | −、＋、−、＋，并转成 int16 | ＋、−、＋、−；保留 int32 完整计数 |
| FWD PWM 符号 A/B/C/D | ＋、＋、−、− | −、−、＋、＋ |
| 纵向/角速度目标上限 | 1.5m/s、6.28rad/s 示例值 | 0.12m/s、0.60rad/s 调试值 |
| 单轮目标 | 未作四轮统一限幅 | 最大 0.12m/s，超限时四轮同比缩放 |
| 异常轮速 | 无此锁存保护 | 任一编码器测速绝对值超过 0.25m/s 即锁存停车 |

培训手册清单写 65mm，而示例保留 100mm，并明确说明换 65mm 轮须改 0.065；本次采用硬件清单。手册“左快右慢左转”的文字与公式矛盾：按 A/C 在左、B/D 在右的约定，正角速度左转应为右侧较快。保留正确公式，没有照抄错误解释。

方向符号是手册代码约定，不是实物验证结果。步骤 8 的“四个正向轮”说明不能单独确定究竟哪两路需要反向；仍须在实际接线下核对“轮子向前转时，经过符号修正的反馈为正”。没有根据一次负反馈就盲目翻转 B/C。

## 实际修改位置

- `Robot/app/ax_robot.h`：采用已有 `Robot/ax_chassis_config.h` 参数，改为 FWD，保留低速调试上限，声明故障和实测控制周期接口。
- `Robot/control/ax_kinematics.c`：按 P30 的 PWM/反馈符号控制，移除 FWD 的 int16 截断，按实际采样周期计算速度，四轮联合限幅；禁用、故障或停车时清除目标和控制器历史。
- `Robot/control/ax_speed.c/.h`：浮点累计 PID 输出，转换为 int16 前限幅到 ±4200，停车清零四路 PID。保留原 Kp=800、Kd=1000，没有假定它们已经适配实车。
- `Robot/app/ax_robot.c`：实测 20ms 控制周期，异常周期、IMU 失败和超速锁存停车；保留第一次故障原因。校准、低压或 EEPROM 操作挂起控制任务前，先禁用运动并停车。
- `Robot/app/main.c`：七个任务优先级均处于 FreeRTOS 的 0～4 范围，增大启动/控制任务栈，检查每次任务创建；启动陀螺校准使用 int32 累加，IMU 正常且启动完成后才使能，先清除启动期间收到的运动目标。
- `Robot/platform/stm32f4xx_it.c`：补齐 SysTick 处理函数声明。
- `Driver/ax_key.c`、`Robot/modules/key/key_gpio_tarkbot.*`：V3.7 的 KA/KB 使用 PE1/PE4；旧式单键接口读取 KA，避免占用 PE0 蜂鸣器。主程序跳过会占用 PB0/PB1 LED 的旧拨码开关初始化。
- `Robot/modules/turn/ax_turn.h`：统一到当前车轮上限；现有 `ax_turn.c` 的量化限幅逻辑保留。该接口不等于主程序已经调用转向动作。
- `Robot/ax_chassis_config.h`：集中说明 0.12m/s 单轮目标限幅和 0.25m/s 应急阈值的区别。
- 根目录旧 `Robot/ax_kinematics.c` 改为实际 `control/ax_kinematics.c` 的兼容入口。Keil 只编译 `control` 版本，禁止把两个入口同时加入工程。
- `Project/xproject.uvprojx`：补入已有但遗漏的 `Driver/ax_imu_bus.c`、`Driver/ax_encoder_extended.c`，输出统一到 `Project/Build/competition.axf/.hex`。原工程曾出现 7 个未定义符号，现已修复。
- `Project/build-arm.ps1`、`build.bat`、`flash.bat`：支持本机 C 盘或 D 盘 Keil/`KEIL_ROOT`，Windows PowerShell 5 的原生工具警告不会被误当成脚本终止；烧录脚本会先重新构建。
- `tests/run_manual_checks.py`、`test_manual_control.c`、`host_platform_manual.h`：保存本次控制回归检查。

没有改动 Camera、FreeRTOS 内核或 STM32 库源码。IMU 双芯片识别、32 位编码器扩展驱动原来已在 Driver 中，本次修复其工程纳入和调用链。当前板级配置沿用 H60 V3.7；此前在板上实际读到 QMI8658，与旧手册 MPU6050 名称不同，因此保留芯片 ID 检测。

## main.py 和超速问题的结论

`Robot` 中没有 `main.py`。实际编译入口是 `Robot/app/main.c`；`Camera/main.py` 是电脑视觉预览，与 STM32 的电机输出调用链不同。

这份新主程序是原有遥控/串口控制程序。KA 短按切换灯效，没有调用此前“加速—90°转向—减速”的 A/B 动作，也没有调用 `AX_RAMP_Apply` 或 `AX_MOTION_Step`。本次保留其功能用途，没有将另一份固件的 A/B 动作移植过来。不要把“斜坡文件被编译”说成“斜坡在电机控制流程中已启用”。

原来可能放大轮速异常的因素包括：车型和编码器换算不匹配、FWD 反馈符号仍为 P60、int16 截断、只限制车体速度而不限制组合后的轮子目标、PID 停车不清历史，以及维护任务挂起控制时留下 PWM。本次修正了这些软件路径。

修正后能保证的是：正常控制中的四轮目标绝对值不超过 0.12m/s；测得任一轮超过 0.25m/s 时切断输出并锁存。**这不能保证实车轮速始终不超过 0.12m/s**。未接入软启动的外部速度命令仍可能阶跃变化，PID 超调、反馈接反、编码器参数不符、接线和惯性都可能造成实际轮速超过目标；20ms 采样保护也存在检测延迟。

此前运行的另一份固件实际读到 `ax_motion_fault=3`，B 轮保留反馈约 −0.292m/s，C 轮约 −0.102m/s。那次故障已经确认属于超速锁存，但反向反馈的物理原因尚未确定。本次没有放宽阈值或直接清除主板故障，不将离线通过称为该实车问题已修好。

故障码：1=IMU，2=控制周期，3=超速，4=任务创建失败。故障后排查并复位；维护过程中禁用运动后不会自行重新启动。
